# แผน: ฟอร์แมตกลางของเรื่อง (Story Format)

เป้าหมาย: ให้ทุกฟังก์ชันที่ต้องอ่าน "เรื่อง" อ่านจากรูปแบบเดียวกัน
แทนที่จะให้แต่ละฟังก์ชันไปปั้นข้อมูลเองจาก `canvas_data` ดิบ

---

## ที่มา และการให้เครดิตให้ถูก

วิธีนี้มาจาก **StoryScope** (arXiv 2604.03136) — *แปลงข้อความเป็น field ตาม JSON schema
ก่อน แล้วค่อยให้ขั้นถัดไปทำงานบน field* เหตุผลคือมันบังคับให้ขั้นถัดไปคิดจาก**เนื้อเรื่อง**
ไม่ใช่**สำนวน**

**ไม่ใช่ NarraBench** — NarraBench ไม่ได้เสนอฟอร์แมตอะไร มันเป็นแผนที่ว่าเรื่องเล่ามีอะไร
ที่วัดได้บ้าง แต่สองอันนี้ต่อกันพอดี เพราะ StoryScope ยืมชุดคุณลักษณะของ NarraBench
มาทำ schema ของตัวเอง

> **StoryScope ให้วิธี · NarraBench ให้คำศัพท์**

สิ่งที่ **ไม่** ยืมมาจาก StoryScope: การคัดเลือก feature ของมันถูกนิยามด้วย label
"คนเขียน/AI เขียน" ถอด label ออกแล้วเกณฑ์คัดเลือกหายไปด้วย — เอามาเฉพาะ *วิธี*
ไม่เอา *ชุด feature ที่มันเลือก*

---

## สองชั้นที่มีอยู่แล้ว

**กระดานพล็อตเป็นเรคคอร์ดตั้งแต่ต้น** — การ์ด เลน จังหวะ เส้นเชื่อม ปม ผู้ร่วมฉาก
ขั้นที่ StoryScope บอกว่าแพงที่สุด (สกัดร้อยแก้วเป็น field) โปรเจกต์นี้ข้ามไปแล้วโดยการออกแบบ

**Export Markdown ที่ทำเสร็จแล้ว คือ IR ที่ใกล้เคียงของจริง** — มีคำนิยามศัพท์ในตัวเอกสาร
รหัสการ์ดที่อ้างอิงได้ frontmatter บอกขนาด ตารางผู้ร่วมฉาก

คำถามจึงไม่ใช่ "จะสร้างฟอร์แมตกลางไหม" แต่คือ
**"จะยกฟอร์แมตที่มีอยู่ จากไฟล์ดาวน์โหลดของนักเขียน ให้เป็นสิ่งที่ทุกฟังก์ชันอ่าน ไหม"**

---

## ผู้ใช้ที่มีจริงวันนี้ — 6 ราย

ฟอร์แมตต้องนิยามจากรายการนี้ ไม่ใช่จากสิ่งที่คิดว่าจะมี

| ผู้ใช้ | ต้องการอะไร | สถานะ |
|---|---|---|
| Export Markdown | ทุกอย่าง + การ render เป็นข้อความ | มีแล้ว |
| ตัววิเคราะห์พล็อต | ปม เลน เส้นเชื่อม ผู้ร่วมฉาก — ต้อง **นับ** ได้ | [แผน](plot-analysis-plan.md) |
| ~~ตัวตรวจขัดกฎพลัง~~ | พลังที่ถูกอ้างในฉาก + กฎที่ scope ตรงกัน | **ติดบล็อก — ดูข้างล่าง** |
| ~~ส่งกฎเข้า AI context~~ | กฎที่เกี่ยวกับพลังในฉากนั้น | **ติดบล็อก — ดูข้างล่าง** |
| ผู้อ่านจำลอง | ตอนก่อนหน้าเท่านั้น (กันสปอยล์) | มีแล้ว ใช้ RAG |
| ผู้ช่วยจัดการข้อมูล | อ้างอิงเอนทิตีข้ามตาราง | มีแล้ว |

**field ไหนไม่มีใครใน 6 รายนี้ใช้ ไม่ต้องใส่** — "ฟอร์แมตเดียวรับใช้ทุกอย่าง"
คือวิธีที่ฟอร์แมตบวมตาย แต่ละรายอยากได้เพิ่มนิดหน่อย แล้วก็เติมกันไปเรื่อย

### สองรายที่ติดบล็อก — ห้ามเอามานิยามฟอร์แมต

ตรวจข้อมูลจริงแล้ว (2026-08-20) **ฉากอ้างถึง "พลัง" ไม่ได้เลย**

| ทางที่น่าจะอ้างได้ | ความจริง |
|---|---|
| สิ่งที่วางในการ์ดบนกระดาน | `character` `dummy_character` `building` `faction` `sticky-note` — **ไม่มี `power`** |
| `scene_element_details.element_type` | `idea_note` `dummy_character` `character` — ไม่มี power |
| `character_powers` | ผูกตัวละคร↔พลัง แต่**ไม่มีคอลัมน์อ้างอิงฉาก** |

ตัวตรวจขัดกฎพลังไม่ได้ "ยังไม่ได้ทำ" แต่ **ยังไม่มีข้อมูลให้ทำ**

ฉะนั้นสองรายนี้ **ห้ามใช้เป็นเหตุผลในการเพิ่ม field** จนกว่าจะตัดสินใจว่าจะให้ฉาก
อ้างพลังได้ยังไง (เพิ่มชนิดลูกในการ์ด? เพิ่ม element_type? ตารางใหม่?)
ฟอร์แมต v1 นิยามจาก 4 รายที่เหลือเท่านั้น

## โครงสร้างคือของจริง Markdown คือการ render

ข้อนี้สำคัญที่สุดในเอกสารนี้

ตัววิเคราะห์พล็อตต้อง**นับ** ปมค้าง เลน ตัวละครที่โผล่ครั้งเดียว
ถ้าให้มันไปอ่าน Markdown แล้ว parse กลับ คือการทำงานย้อนทางและเปราะ

```
buildStoryFormat()  ──┬──> renderMarkdown()   → ให้ LLM อ่าน / ให้นักเขียนโหลด
   (โครงสร้างจริง)     ├──> ตัววิเคราะห์พล็อต    → นับตรงจากโครงสร้าง
                       ├──> ตัวตรวจขัดกฎ
                       └──> AI context
```

Export ปัจจุบันคือ `renderMarkdown()` ที่ผูกติดกับ state ของคอมโพเนนต์อยู่ —
งานคือแยกส่วนประกอบข้อมูลออกมาให้เรียกได้จากฝั่ง server

## กระดานมาก่อน ร้อยแก้วมาทีหลัง — สวนทางกับเปเปอร์ และตั้งใจ

StoryScope เริ่มจากร้อยแก้วแล้วสกัดเป็น field แต่ข้อมูลจริงของโปรเจกต์นี้กลับด้าน
(วัดเมื่อ 2026-08-20 · นิยาย 275aeebd)

| | จำนวน |
|---|---|
| ตอนที่เขียนแล้ว (`notes`) | **1** |
| การ์ดบนกระดาน | **89** |
| ฉาก · ปม | 5 · 7 |
| `note_stylometry` | **0** |

IR ที่สกัดจากร้อยแก้วตามเปเปอร์จะแทบไม่มีอะไรกิน ส่วน IR ที่ประกอบจากกระดาน
มีข้อมูลครบตั้งแต่วันแรก — ร้อยแก้วค่อยไหลเข้ามาเป็นชั้นเสริมเมื่อเขียนมากขึ้น

## รูปร่างคร่าวๆ

ยังไม่ล็อก ตั้งชื่อ field ตาม aspect ของ NarraBench เพื่อให้คุยกับงานวิจัยรุ่นถัดไปได้

```
StoryFormat
  formatVersion            "1"
  novel      { id, title }
  cast       [{ alias "@A", name, type, cardCount }]     ← Agent
  threads    [{ id, title, status, roles: [seed|reinforce|payoff] }]  ← Plot
  scenes     [{
      code "S01", id, title, goal, conflict, outcome, causeFrom       ← Event
      beats [{
          code "C01", beatIndex, lane, title, content                 ← Structure
          isNarration, keyMoment                                      ← Narration
          simultaneousWith [ "C02" ]
          participants [{ alias, name, type, action, goal, outcome }]
          links        [{ to "C03", kind, label }]
          threadTouches[{ threadId, role }]
      }]
  }]
```

**ไม่เก็บ coverage ไว้ในฟอร์แมต** — มันหาได้จากตัวฟอร์แมตเองอยู่แล้ว
เก็บซ้ำคือของที่จะไม่ตรงกันวันหนึ่ง

**ไม่มี field เกี่ยวกับพลัง ใน v1** — ดูหัวข้อสองรายที่ติดบล็อก

**ตัวย่อ `@A` อยู่ในฟอร์แมต ไม่ใช่ในตัว render** — เพราะทุกผู้ใช้ที่ส่งข้อความให้ LLM
ได้ประโยชน์เหมือนกัน วัดกับ tokenizer ของ `llama-3.3-70b` จริง: ชื่อเต็ม 5 โทเคน/ครั้ง ·
`[A]` 2 · `@A` 1 — และ `@` คือสัญลักษณ์ที่แอปใช้อ้างถึงตัวละครอยู่แล้วในโน้ตบนกระดาน

## สร้างเมื่อไหร่ และเก็บไว้ไหม

**สร้างสดทุกครั้งที่เรียก ไม่แคช**

เหตุผล: มันคือการประกอบเรคคอร์ดที่มีอยู่แล้ว ไม่ได้เรียกโมเดล ไม่ได้คำนวณอะไรหนัก
ฉากใหญ่สุด 19 การ์ด — ประกอบเสร็จในหลักมิลลิวินาที

และกระดาน autosave ทุก 2 วินาที ถ้าแคชไว้จะต้องมีกลไก invalidate ที่ผิดพลาดได้
แล้วจะกลายเป็นบั๊ค "ตัววิเคราะห์เห็นข้อมูลเก่า" ที่หายากมาก — แลกไม่คุ้มกับมิลลิวินาทีที่ประหยัด

**สิ่งที่แคชคือ *ผลวิเคราะห์* ไม่ใช่ตัวฟอร์แมต** — echo score ที่จ่ายเงินไปแล้วต้องเก็บ
(ดู [plot-analysis-plan.md](plot-analysis-plan.md)) ส่วนตัวฟอร์แมตสร้างใหม่ได้ฟรีเสมอ

## เวอร์ชัน — บังคับ

StoryScope ระบุว่า **ค่าเทียบกันได้เฉพาะภายใต้ schema และ prompt เดียวกันเป๊ะ**

- `formatVersion` ต้องอยู่ในผลลัพธ์เสมอ
- ผลวิเคราะห์ทุกชิ้นที่เก็บลง DB ต้องบันทึกเวอร์ชันที่ใช้ตอนคำนวณ
- ขึ้นเวอร์ชันทุกครั้งที่เปลี่ยนความหมายของ field — ไม่ใช่แค่ตอนเพิ่ม field

มีแบบอย่างในโปรเจกต์แล้วคือ `PROMPT_VERSION` ใน ai-review

## ลำดับการทำ

| # | งาน | ได้อะไร |
|---|---|---|
| 1 | แยกส่วนประกอบข้อมูลของ export ออกจากคอมโพเนนต์ → `lib/story-format.ts` | เรียกจากฝั่ง server ได้ · ทดสอบได้ |
| 2 | `renderMarkdown(format)` — ย้าย logic เดิมมารับ format แทน state | export เดิมทำงานเหมือนเดิม ไม่มีอะไรพัง |
| 3 | ขยายจากรายฉากเป็นทั้งเรื่อง | ปมกับความซ้ำข้ามฉากดูได้ |
| 4 | ตัววิเคราะห์พล็อต Phase 1 อ่านจาก format | ผู้ใช้รายแรกที่ไม่ใช่ export |

ข้อ 1–2 ไม่เปลี่ยนพฤติกรรมอะไรเลยที่ผู้ใช้เห็น เป็นการจัดบ้านล้วน —
ถ้าทำแล้วปุ่ม export ยังได้ไฟล์เดิมเป๊ะ แปลว่าถูก

## นอกขอบเขต

- **ไม่สกัด field จากร้อยแก้วด้วย LLM** — เป็นขั้น templatize ของ StoryScope ซึ่งจำเป็นเมื่อ
  ต้นทางเป็นข้อความล้วน แต่กระดานเป็นเรคคอร์ดอยู่แล้ว ไม่ต้องจ่าย
- **ไม่ทำ cross-source comparison / feature discovery** — สองขั้นหลังของ StoryScope
  ขั้นที่สามแพงที่สุด (เปเปอร์เองจำกัดที่ 600 เรื่อง) ยังไม่มีเหตุผลจะแตะ
- **ไม่แตะชั้น stylometry** — คนละชั้นกัน StoryScope วัดไว้ว่าเขียนกลับข้อความเพื่อลบสไตล์ทิ้ง
  แล้วการจำแนกตามคุณลักษณะเชิงเรื่องแทบไม่ขยับ โครงสร้างเป็นอิสระจากลีลา
  ฟอร์แมตนี้อยู่เหนือทั้งสองชั้น ไม่ได้อยู่ในชั้นใดชั้นหนึ่ง

## ความเสี่ยงที่รู้ตัว

**ฟอร์แมตบวม** — ทางกันคือกฎข้อเดียวข้างบน: field ไหนไม่มีใครใน 6 รายใช้ ไม่ต้องใส่
ทบทวนรายการผู้ใช้ทุกครั้งที่จะเพิ่ม field ไม่ใช่เพิ่มเพราะ "น่าจะมีประโยชน์"

**ฟอร์แมตกลายเป็นคอขวด** — ทุกฟีเจอร์ต้องรอมันเสร็จก่อน ทางกันคือลำดับข้อ 1–2
ที่ไม่เปลี่ยนพฤติกรรมอะไร ทำเสร็จแล้วของเดิมยังทำงานได้ทันที

**ข้อมูลจริงยังน้อย** — 5 ฉาก 1 ตอน การออกแบบฟอร์แมตจากข้อมูลชุดเล็กเสี่ยงที่จะไม่ครอบ
เคสที่โผล่ตอนเรื่องยาวขึ้น ยอมรับความเสี่ยงนี้ เพราะการรอให้ข้อมูลเยอะก่อนแปลว่าทุกฟีเจอร์
ต้องปั้นข้อมูลเองไปอีกนาน — และ `formatVersion` มีไว้รับมือกับตอนที่ต้องเปลี่ยน
